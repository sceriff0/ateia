Ranking three registration backends on real tissue: a factored arm design, the shared metric that makes it answerable, and the stage vocabulary that does not align

S1 · pipeline S2 · registration S3 · quality control S4 · lazy reads S5 · benchmark arms

Two harnesses answer two questions. sweep.yaml rescales synthetic images across a size × channel matrix to fit the cost model that sizes the resource directives. arms.yaml registers the real study slides once per configuration to decide what to ship. This figure is the second. Its central problem is not compute: it is that a cross-backend ranking needs one metric all three backends can be scored on, and the obvious column — "the final stage" — does not mean the same thing in each.

a

The comparison you cannot afford to run

The instinctive design is a full cross-product: every backend × every knob × every segmenter, then read off the best number. On real whole-slide images that design is unaffordable and, worse, confounded.

the instinct
cross everything
3 backends × their knobs × 3 QC segmenters × 3 segmentation backends, per patient.
why it is unaffordable
the expensive half repeats
Crossing a cheap axis against an expensive one re-pays for the expensive one at every level of the cheap one.
why it is confounded
segmentation arms differ
Comparing segmenters across runs that also registered differently measures the two together.
observed on real slides: REGISTER 483 GB MERGE_AND_PYRAMID 6.5 h every count below is per patient — read them as cohort multipliers
b

Factored, never crossed — each stage paid for once

Three arms, each answering one question, each resuming from work an earlier arm already did. The step gate (--start / --stop, figure S1 panel b) is what makes the factoring possible: an arm runs only the step it varies.

arms.yaml→build_arm_plan.py→ arms.csv→run_arms.sh→ 16 runs / patient→make_tables.py→paper_data/*.csv

Arm 1 — registration

--start registration --stop registration
  • 9 arms: 6 VALIS + 2 ASHLAR + 1 STARE
  • All resume from one shared preprocessing run (preprocess_shared)
  • Nothing downstream of registration is run — it cannot change the staged registration QC
  • reg_qc=2 still segments the native slides, but inside the registration step

Arm 2 — segmentation

--start segmentation
  • 3 arms: instantseg / stardist / cellsam
  • All resume from one registration arm's csv/registered.csv
  • from_arm = valis_high_micro2 — the configuration intended to ship
  • So the segmenter comparison is not confounded by differing registration

Arm 3 — compute profile

no step gate; full pipeline, traced
  • 1 arm (compute_all), repeats: 1
  • The only arm that measures what the other two skip: SEGMENT, quantification, export, MERGE_AND_PYRAMID
  • Rows join the synthetic sweep's tables as varied_axis=real_compute
  • Two patients bracketing the size range give a 2-point anchor against the synthetic fits

c

The registration arm — three backends, one metric

A cross-backend ranking is answerable at all only because the seg-overlap scorer is method-agnostic: bin/warp_seg_qc.py takes --method and builds its warper from a VALIS pickle or a STARE-style M0 + mesh manifest. ASHLAR joins the table because bin/ashlar_solve.py rewrites its per-tile placements into that same manifest.

9 registration arms — a grid, and two single points
VALIS — 6 armsthe grid
memory_mode × reg_micro_reg = 2 × 3. Not a 2×2. reg_micro_reg is a depth (0 none, 1 micro-rigid, 2 + micro non-rigid), and memory_mode low/high are different feature matchers — BRISK/RANSAC versus SuperPoint/SuperGlue — not one matcher at two resolutions.
memory_mode low, highreg_micro_reg 0, 1, 2
ASHLAR — 2 armsexternal baseline
A backend, not a cell of the grid above: it has neither VALIS-only param and carries NA for both. Fans out over tile_size because that is its fairness knob (panel e). Arm names embed the tile (ashlar_tile1024) because the consumer falls back to parsing the directory name when the manifest is missing — two arms differing only by an unread column would render as one duplicated box.
tile_size 1024, 4096overlap 0.1max_shift_um 30
STARE — 1 armat its defaults
The other in-house backend, one point of comparison against the whole VALIS grid. Also carries NA for memory_mode and reg_micro_reg.
tiled_defaults
BLANK IS NOT ZERO. VALIS_ONLY = memory_mode, reg_micro_reg; ASHLAR_ONLY = reg_ashlar_tile, reg_ashlar_overlap, reg_ashlar_max_shift_um. Each is written blank on every arm of the other backends, so the consumer can tell not applicable from at default — and so run_arms.sh's blank-guard never passes a VALIS run --reg_ashlar_tile "", which schema validation rejects.
d

The backends do not share a stage vocabulary

Every arm emits accuracy per transform stage, and the ranking reduces each run to its final, most-registered stage. But the stage names come from lib/WarpBackends.groovy, and the three backends do not use the same ones. Only native and rigid are shared as both a spelling and a meaning.

backendstage vocabularyterminal stagerank
valisnative → rigid → non_rigid → micromicro3
tiled (STARE)native → rigid → refinedrefined2
ashlarnative → rigid → refinedrefined2
A LIVE BUG, NOT A GAP WAITING FOR ASHLAR. _STAGE_RANK was missing refined. An unranked stage maps to −1 via .fillna(-1) — the same rank as native, which is also unranked when missing — so sort_values("_rank").groupby(…).tail(1) picked STARE's terminal stage by nothing but the stable-sort tie-break happening to place it after native. Every STARE run in the paper tables was one upstream reordering — a different glob order, a pandas version whose sort is not stable here — away from reporting its unregistered accuracy as its headline number. Nothing failed, and nothing would have.

The fix

benchmarks/analysis/lib/quality.py
  • native 0 · rigid 1 · non_rigid 2 · refined 2 · micro 3
  • non_rigid and refined share rank 2 deliberately: both are "one non-rigid step past rigid", in different backends' spellings
  • Ranked, not derived — the order is a fact about the backends, not about any one table

The guard

benchmarks/tests/test_stage_rank_covers_every_backend.py
  • Reads the stage vocabularies out of WarpBackends.groovy rather than restating them
  • A fourth backend with a new stage name fails this test instead of silently degrading the table
  • Includes a test that the scanner itself still finds the vocabularies — a guard that cannot fire is not a guard

The consequence for reading the table

paper_data/registration_accuracy.csv
  • Each arm is ranked on its own final stage — the stage column is not a shared axis
  • Read ASHLAR against VALIS's rigid for the like-for-like number
  • Read it against micro to quantify what non-rigid buys
  • Reporting only the second overstates VALIS's advantage
e

Tile size is a fairness knob, not a cost knob

Most benchmark knobs trade compute for accuracy within one method. Grid granularity does not: it changes how much freedom a piecewise method has, so setting it differently across backends silently decides the result before any slide is read.

ASHLAR computes one shift per tile
Its transform is piecewise translational, so a finer grid buys it more local freedom — strictly more expressive, not merely slower.
reg_ashlar_tile
STARE solves a mesh per tile
The direct analogue: tile core size sets both the fan-out and the mesh resolution.
reg_tiled_tile
So they must be bracketed, not fixed
ASHLAR is swept at 1024 and 4096 — the two ends of STARE's swept range [1024, 2048, 4096] — rather than pinned at one value.
a list, not a scalar
Otherwise the comparison is pre-decided
ASHLAR at a fine grid against STARE at a coarse one is not a backend comparison; it is a granularity comparison wearing one.
the trap
CARRIED INTO THE TABLES. reg_ashlar_tile is in both make_tables.py's CONFIG_COLS and run_cost_summary's carry list — without it, two ASHLAR arms differing only by tile size collapse into indistinguishable rows.
f

Who found the nuclei? — a robustness axis, not a quality claim

The registration accuracy is measured on segmented nuclei, and SEG_QC_SEGMENT is SEGMENT under an alias — so params.seg_method chooses the measuring instrument. Varying it leaves the registration byte-identical and changes only how it is observed.

what changes
the instrument
instantseg → stardist → cellsam, on an identical registration.
what it can say
is the verdict stable?
If the arm ranking survives a change of segmenter, the headline number is robust.
what it cannot say
nothing about registration quality
A better segmenter does not make a registration better. This is never a quality claim.
cross: reference → 2 extra runs (the reference arm only) cross: all → every arm × 3 reference_arm = valis_high_micro2 start at reference: if stable there, crossing all buys a denser null result
g

Scoring segmentation on tissue with no ground truth

Real study slides have no annotated masks, so the segmentation arm cannot be scored against truth. Two reference-free signals are used instead, and they answer different questions.

agreement

→ paper_data/segmentation_agreement.csv
  • Cross-method cell-count ratio and instance F1
  • Needs no new code and no ground truth
  • Answers "do the backends agree, and where do they not?"
  • Cannot rank — three backends agreeing can be three backends wrong together

cse

CellSegmentationEvaluator · optional
  • A reference-free quality score, so it can rank rather than only compare
  • Off by default: needs the segeval container published and skip_seg_quality_eval=false
  • Its QualityScore drifts with any downsample factor applied

the compute profile

→ runs_master.csv · scaling_fits.csv
  • Per-process peak RAM and wall-time from the Nextflow trace
  • Real-tissue rows sit beside the synthetic sweep's, tagged varied_axis=real_compute
  • The only check that the synthetic scaling fits transfer to tissue at all

What this benchmark cannot tell you

Stated so a reader does not infer completeness from the size of the table.

no ground truth
registration & segmentation
  • Every accuracy number is a reference-free proxy — seg-overlap of matched nuclei, not landmark error
  • Public-landmark TRE (ANHIR / ACROBAT) is a separate external check, not part of these arms
no non-rigid ASHLAR
the baseline's ceiling
  • ASHLAR attempts no non-rigid warp at all — only a piecewise translation per tile
  • Its arm cannot be read as "ASHLAR's best" against VALIS's best; it has no non-rigid mode to lose in
one cohort, one site
generalization
  • maximum_shift_um = 30 must exceed the real cross-cycle drift for your cohort
  • Set too small it does not error — LayerAligner substitutes a model prediction and degrades silently
a ranking, not a significance test
statistics
  • repeats: 1 by default: no per-process variance, no error bars on cost
  • Arm ordering on a handful of patients is a point estimate, not a tested difference
AND ONE THING THE PIPELINE ITSELF DOES NOT DO: ASHLAR is a benchmark baseline, not a production backend. mode=add_cycle rejects every method except valis — an allowlist, since the earlier denylist named only tiled and would have let an ashlar run register silently with VALIS under ASHLAR's name.

Supplementary Figure S5. The real-sample arm benchmark. (a) A full cross-product of backends, knobs and segmenters is both unaffordable on whole-slide images — REGISTER has been observed at 483 GB and MERGE_AND_PYRAMID at 6.5 h — and confounded, because comparing segmenters across runs that also registered differently measures the two together. (b) The design is therefore factored: three arms, 16 runs per patient, each expensive stage paid for once. Nine registration arms resume from a single shared preprocessing run; three segmentation arms resume from a single registration; one untruncated traced run supplies the per-process cost profile. (c) Ranking three backends against one another is possible only because the seg-overlap scorer is method-agnostic — it builds its warper from a VALIS pickle or an M0 + mesh manifest — and because ASHLAR's per-tile placements are rewritten into that same manifest rather than scored out of band in a different metric family. Parameters belonging to one backend are written blank, never zero, on the others. (d) The backends do not share a stage vocabulary: VALIS emits native/rigid/non_rigid/micro, the manifest backends native/rigid/refined. refined was absent from the rank table, so it collapsed to the same rank as the unregistered native stage and the terminal stage was selected by a sort tie-break alone; every STARE row was one upstream reordering away from publishing its unregistered accuracy as its headline number. The rank table now covers both vocabularies and a test derives the expected stage names from lib/WarpBackends.groovy so a fourth backend fails loudly instead of degrading the table. (e) Grid granularity is a fairness knob rather than a cost knob — a finer grid makes a piecewise method strictly more expressive — so ASHLAR is swept at both ends of STARE's range instead of pinned. (f) Varying the QC segmenter leaves the registration identical and changes only the instrument observing it; it is a robustness axis on the headline number and never a quality claim. (g) With no annotated masks, segmentation is scored by cross-method agreement, which compares but cannot rank, and optionally by a reference-free quality score, which can. (i) Every number here is a reference-free proxy on one cohort at a single repeat: a ranking, not a significance test.
