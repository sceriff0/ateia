# Peak-RSS measurement record — 2026-08-26

Tracked record of the measurements behind `perf/rss-and-format-2026-08-26`. This is a
measurement record, not a narrative — it exists so code comments and tests can cite a document
that is actually in the repo, instead of the untracked planning scratch
(`PERF-PLAN.md`, `.superpowers/sdd/perf-rss-2026-08-26/`) those files used to point at.

All numbers below were re-measured against the code as shipped on this branch, in isolated
processes, not carried over from planning estimates.

## QUANTIFY's per-label median: 4.15x

`bin/quantify.py`'s per-compartment median moved from a per-label
`scipy.ndimage.labeled_comprehension` callback (still present as the fallback path for any
dtype other than uint16) to `_median_per_label_from_sorted`: a composite-key sort of
`(label, value)` pairs, reading each label's median directly off contiguous sorted runs — no
per-label Python callback on the hot path.

Method: both variants isolated in separate processes, same synthetic label/value arrays.

| Path | Wall time |
|---|---|
| Fallback (`labeled_comprehension`) | 1.879 s |
| Fast path (composite-key sort) | 0.453 s |

**4.15x faster.** Outputs identical at `rtol=0, atol=0` (`equal_nan=True`) against an
independently-recomputed `np.median` reference and against a verbatim copy of the prior
per-pixel pandas-groupby implementation — see `tests/test_quantify_median.py`.

The fast path only handles uint16 (it composes `(label << 16) | value`, which needs 16 spare
bits); any other dtype takes the `labeled_comprehension` fallback.

## Segmentation mask writers: tiled vs. striped

`bin/segment.py`, `bin/segment_cellsam.py`, `bin/segment_instantseg.py` and
`bin/extract_mask_series.py` write the nuclei/cell mask with `tifffile.imwrite`. Before this
branch none of the seven call sites passed `tile=`, so tifffile fell back to strips — the mask
is the highest-fan-out artifact in the pipeline (read back by `QUANTIFY` once per marker,
`EXTRACT_CELL_PROPERTIES`, `EXTRACT_NUCLEI_PROPERTIES`, `SEG_QC_GEOJSON`, `EXPORT_GEOJSON`,
`EXPORT_SPATIALDATA`, `SEG_QUALITY_EVAL`, `WARP_SEG_QC`).

Measured on a 6000² uint32 mask with realistic Voronoi cell geometry (14,000 cells, 56%
foreground), zlib compression held constant on both sides (G2):

| Layout | Write | Whole read | Size | 4× 2048² window |
|---|---|---|---|---|
| striped (before) | 0.12 s | 0.10 s | 2.80 MB | 0.146 s |
| tiled 1024² (after) | 0.06 s | 0.04 s | 2.26 MB | **0.019 s** |

Tiling is free on file size, halves write time, and makes windowed reads (the pattern every
consumer above actually uses) 7.7x faster. `MASK_TIFF_TILE = 1024` was measured directly at
this size — it is not simply copied from `CONVERT_TIFF_TILE`/`WRITE_TILE`'s 2048, because a
smaller tile trades a slightly larger per-tile-boundary read-amplification for finer-grained
windowed access, which is the mask's actual read pattern (many small per-cell/per-region reads,
not whole-plane decodes).

## `read_decimated` (QC lazy read): pre-allocation kept, dtype narrowing reverted

### Methodology

A 7000×6000, 2-channel uint16 OME-TIFF pair (~168 MB per file on disk; one full-resolution
plane is ~80 MiB as uint16 / ~160 MiB as float32), built once and reused across all variants.
Each measurement is a **fresh `python3 -c` subprocess** (never reused across variants) reading
`resource.getrusage(resource.RUSAGE_SELF).ru_maxrss` at the end (bytes, macOS/Darwin host).

### What changed

`bin/utils/tiled_io.py::read_decimated` used to build its output as a Python list of per-band
arrays and a final `np.concatenate` — a transient second full-size buffer at every factor. It
now writes each streamed band directly into a single pre-allocated `np.empty` destination.
Pure win, no dtype change: still unconditionally `float32`.

A `dtype=` parameter narrowing the read to uint8/uint16 for `bin/utils/qc.py`'s caller was
tried and **reverted** — see "Why the dtype narrowing was reverted" below.

### Read-only phase (`open_lazy` + `read_decimated` × 2, no render), 3 fresh runs each

| Variant | Runs (MB) | Mean (MB) |
|---|---|---|
| Before (list + concatenate, always float32) | 670.3, 671.5, 670.7 | 670.8 |
| Shipped (pre-allocated, always float32) | 510.5, 509.8, 510.9 | 510.4 |
| Narrow read, never widened back (not shipped — G1-violating) | 349.8 (1 run) | 349.8 |

**Pre-allocation alone: -23.9% (670.8 -> 510.4 MB), reproducible** (spread <=1.2 MB / 0.2%
across 3 runs in both variants). This is the number that actually ships.

The narrow-read variant (349.8 MB) is included for context only — it is not shipped, and is not
value-preserving on its own (see below).

### Why the dtype narrowing was reverted

`bin/utils/qc.py::create_registration_qc`'s only consumer of `read_decimated`'s output is
`autoscale_for_display`, which runs its min-max arithmetic directly on whatever dtype it is
handed — a uint16 input promotes to float64 under true-divide; a float32 input stays float32.
Those are different intermediate precisions, and they demonstrably round
`np.round(normalized * 255)` differently for real data.

**Reproduced counter-example:** `min=13286, max=62449, value=52520` — the uint16-driven
(float64-promoted) path returns `203`; the float32-driven path returns `204`. Root cause: the
float32 arithmetic rounds a true value just under `x.5` up to an exact float32-representable
`x.5` (a tie float32 doesn't have the precision to see is spurious), and `np.round`'s
round-half-to-even then resolves that manufactured tie the other way. Found by an exploratory
sweep of ~8.87M values across 400 random `(min, max)` ranges: 2 mismatching pixels, max
`|diff| = 1`. Pinned by
`tests/test_tiled_io.py::test_autoscale_uint16_vs_float32_disagree_at_a_real_triple` and
`tests/test_registration_qc_lazy_read.py::test_qc_output_is_exact_at_the_known_adversarial_pixel_triple`.

So a narrow read is only G1-safe if `qc.py` widens it back to float32 before
`autoscale_for_display` runs. That widen-back was implemented once, and measured: at the
read-only phase, widen-back-included narrowing landed at the **same** 670.8 MB as never
narrowing at all — the widen-back cast materializes the full float32 plane and erases the
saving the narrow read appeared to offer. Once corrected for G1, the narrowing bought nothing
and only added a cast plus branching, so it was dropped; `read_decimated` unconditionally
returns float32 again and `qc.py` never narrows.

### End-to-end: no measured improvement

Full `create_registration_qc` (read + fullres autoscale/stack/TIFF write + downsampled
overlay/PNG write), 3 fresh runs each, same fixture:

| Variant | Runs (MB) | Mean (MB) |
|---|---|---|
| Before | 1329.6, 1228.2, 1251.0 | 1269.6 |
| Shipped | 1346.3, 1337.7, 1315.3 | 1333.1 |

Shipped's mean is ~5% *higher* than before's, but the per-run spread (before: ~100 MB / 8%;
shipped: ~31 MB / 2%) means this is noisy at 3 runs per variant. **Honest statement: the
shipped, G1-compliant fix shows no measurable end-to-end peak-RSS improvement over the
pre-branch baseline in this benchmark; the point estimate trends slightly higher, within
noise.** The pre-allocation win is real and reproducible at the read-only phase (-23.9%); it
does not carry through to the full render-and-write pipeline, which is dominated by other
allocations (the fullres float32 stack and TIFF/PNG writes).
