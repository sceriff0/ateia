Why one worktree, not two

A worktree-isolated session refuses every git operation whose target is outside its own worktree — git -C and cd && git alike — and EnterWorktree only accepts paths under .claude/worktrees/. Two worktrees were created for this work and had to be removed. Switching branches inside the single worktree is the available shape; plan for it rather than against it.

Two Phase 8 blockers, found while closing Phase 7

The sweep could not launch on Nextflow 26 at all. Both runners passed every axis as --<name> <value>, and NF26 delivers every CLI param as a String — not just booleans. It would have failed at launch, on the cluster, after the input matrix had already been generated. They build a -params-file now.

The arms and the sweep still shared a hand-off root on the cluster path. Commit 103e47c separated them in the Makefile and reads as though that closed it; it never touched either submit script. And it was both halves — tables and figures — not just the tables the review named.

Read this before the next phase

Five traps, each with the measurement that caught it

Not a sequence — a set. Every one of these was specified by the plan or believed by the code, and every one was only exposed by running the thing rather than reading it. Four of the five pass every static guard in the repo.

enabled: { … } in a publishDir is silently false

Nextflow does not resolve a closure in enabled: the way it does in path: or saveAs: — it coerces the closure object, which comes out false. The plan specified the closure form. It makes --cleanup_level=none a no-op, which breaks every --start and every add_cycle chain, while the run exits 0.

enabled: { … } → 30 files at BOTH levels enabled: <expr> → 30 at final, 62 at none

task.clusterOptions recurses

Read from inside a clusterOptions closure it is self-referential. It does not fall back to the profile value — it crashes. The plan specified exactly that form, so shipping it would have traded a missing --account for a dead GPU path.

NXF_VER=26.04.6 java.lang.StackOverflowError task failed, run aborted

cleanup_work=true breaks nf-test wholesale

Nextflow empties the work directory at session teardown, and nf-test hashes its snapshot files after the session exits. Every snapshot(…) that recorded an md5 recorded a bare path instead. conf/test.config pins both cleanup params away from the shipped defaults, the way it already pins seg_method.

78 of 221 stub tests failed — all on snapshot mismatch alone

NF26 stringifies every CLI param

Known for booleans; it is true of integers too, and the benchmark runners passed about forty axes that way. 25.04.7 accepts them, 26.04.6 does not. Anything that builds a Nextflow command line by hand is suspect until checked on both engines.

--reg_qc (1): Value is [string] but should be [integer]

A guard can be inert and green

tests/lib_probe.nf — the only unit-test surface lib/*.groovy has — did not compile under NF26, so every assertion in it was skipped in CI's latest-everything leg. Separately, two fixtures had been referenced with checkIfExists: true and produced by nothing since cea0b47.

assert cond, 'msg' → NF26: parse error closure(x) → NF26: not defined

Phase 8

What it costs, and what will bite

The run count is measured from the plan builder rather than counted by hand, so it moves when sweep.yaml does:

python3 -c "import yaml; from benchmarks.build_run_plan import build_run_plan; \ print(len(build_run_plan(yaml.safe_load(open('benchmarks/configs/sweep.yaml')), repeats=3)))" # 414
  • 138 configs, 414 runs at three repeats, on the synthetic matrix. The ashlar arm added 9 of those configs.
  • The real cohort is separate and dearer. The arms run whole slides: REGISTER has been observed at 483 GB and MERGE_AND_PYRAMID at 6.5 h.
  • Two known cliffs. MERGE_AND_PYRAMID is an absolute node-memory limit around 450 GB, not cgroup pressure; REG_WARP_REF OOMs on merged high-LZW multi-channel references. Historically about 19.6% of reserved GB·h has been lost to OOM-retry behind green builds.
  • The cluster path pins NXF_VER=25.04.7. Its stated reasons were stale and are corrected in place, but the pin stays: nothing has run on 26.x on that cluster, and lifting it is an experiment, not an edit. Do one arm first.

A decision worth making before spending the runs

The ashlar grid is 9 configs the paper did not previously buy. sweep.yaml argued against it — "not a configuration this project ships" — but nextflow_schema.json lists ashlar in registration_method's enum, so a user can select it. Measuring it is one option; removing it from the enum so the pipeline stops offering it is the other. Leaving it selectable and unmeasured is the only option that is not honest, and a guard now fails on that state.
